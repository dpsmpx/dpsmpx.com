Ecosystem progress

Draft: not approved by the author — will not appear on the live site.

From 11 September to 9 October 2026 one game grew into an ecosystem of repositories — the core, control, a sync layer and a support layer. This page shows what was built — from git history measurements and the projects' own documents.

The period runs from 11 September 2026 to 9 October 2026, from the first commit of Galdhold (formerly VoxelRPG) to the snapshot at 9 October 2026, 19:00 Moscow time. That is 28 days; the charts show 29 calendar dates, and the last one is partial.

Only the current system is counted — repositories started together with the game repository and after it, except those the author removed. Earlier projects and the removed ones form an archive: they are not counted or charted, and the method section names them — their repositories are open.

The numbers here are measurements of git history and of the projects' own documents; derived values follow the formulas in "How it was measured". A commit count is not a measure of value, so progress is shown through several measurements at once: work per day, branches, code, checks, decisions, structure.

Snapshot on 9 October

Where the projects stand now. Stages come from the projects' own documents, with a date. There are no readiness percentages: the projects do not define them.

Every day

Over the period — 1,313 commits by the author and Claude across all branches and 245 merged pull requests; there were commits on 28 of 29 days. Until 3 October Galdhold was the only repository in the count. From 3 October new core repositories appear, from 5 October control, the sync layer and the support layer; 5 October 2026 is the peak: 167 commits and 39 pull requests.

The columns are split into three groups — Galdhold, the rest of the core and everything outside the core (control, the sync layer and the support layer) — so that work outside Galdhold does not disappear against it: Galdhold accounts for 57% of all commits. A commit is a unit of history, not a measure of quality: one commit can be a line in a document, another a new system.

Accumulation

How much has been done since the start of the period. Core repositories with work reached 9; 8 of them appeared after the first day. In total, 13 repositories with work are counted.

Where the work happened

A row is a repository, a cell is a day; colour is the number of commits on one scale for all rows. The core is on top; control, the sync layer and the support layer below. Forks of other people's projects, personal repositories and the archive are not counted.

Who writes the code

Most commits are made by Claude sessions: 81%. Commits under the author's name include both manual work and other tools under the author's account; git cannot tell them apart. What the author does shows not in the commit count but in the decision logs below.

Parallel work in branches

Each AI session works in its own branch and merges the result into the main branch through a pull request in small batches. In the first three weeks commits went into no more than 3 working branches a day; at the peak, into 26. A commit made directly on the main branch does not count as a working branch. The median time from a batch's first commit to the merge is 31 min; 68% of pull requests were merged within an hour.

An unmerged branch is not a result yet, so it is shown separately, as of the snapshot. Branch history can only be reconstructed from merges and surviving branches: deleted unmerged branches are not counted.

Code, tests and documents

Lines of text files in the core's main branches at the end of each day: 35k at the start, 440k now. The jumps on 3–4 and 6 October are new core repositories with their own code and documents. This is the core's volume: control, the sync layer and the support layer are not included. Volume shows the scale of the implementation, not its quality. Data, schemas and run logs are not included.

Checks

What checks the code grew along with it: lines in the core's test files went from 1.1k to 102k. Galdhold has its own automated check command: according to the game's README there were 100 checks, now 6,042.

These are different measures, and there is no overall quality score here. Test lines do not compare projects with each other, and the Galdhold check count is the project's own record on the dates it changed; there are no values between those dates.

Decisions and knowledge

Until 29 September 2026 the core had no decision logs; at the snapshot they hold 279 entries. DPprofile is a verifiable history of the development path — sources, facts, timeline. DPmeta holds the ecosystem map, contracts between repositories and risks; it is the sync layer, so its log is not in this sum, and its documents are in the counters below.

Ecosystem map

The ecosystem has four parts: the core — the upper part of the snapshot table above; control, the sync layer and the support layer — its lower part. Control stands apart: DPmetaApp is ecosystem control: the author's personal Android app — at the specification stage. The sync layer is DPmeta. The support layer: DPvisualisation is an interactive model of the ecosystem on real data; DPmonetization is project portfolio analysis: from evidence to decision — core skeleton. The map below shows layers by purpose: control and sync have their own layers, and the support layer sits in the engineering foundation.

The repositories are independent: no repository depends on another to build or run. Each builds and is checked on its own; they are connected by decisions, contracts and facts. A diagram of the links, built from data, is in the "Ecosystem" section.

Milestones

Milestones are events with sources: a decision, a release, a measurement, a new repository. They are not measurements, and on the daily chart they are only marked.

How it was measured

The dataset is collected by the system's own tool from repository clones; it is stored with the site, and the page is built from it at build time, without calls to GitHub. Only the current system is counted; the archive — early open projects and the removed ones — is named in the method but not counted. A private project without a public name is counted only in totals; branch names, commit messages and the time of day of commits are not published. Later snapshots are new datasets with the same formulas; past ones are not recalculated.
