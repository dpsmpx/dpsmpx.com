# Решения DPprofile

Журнал решений о самом репозитории: что он хранит, как и чем это
проверяется. Решения о проектах автора здесь не принимаются — они
записаны в их собственных репозиториях и попадают сюда только как
факты (`docs/facts/`).

Правила журнала:

- Номер не переиспользуется и не меняется. Новое решение — следующий
  свободный номер (сейчас — **19**).
- Решение не переписывается задним числом. Если оно меняется, старое
  получает статус «заменено D-NN», новое объясняет, что изменилось и
  почему.
- У каждого решения есть **проверка** — скрипт `tools/verify/`, который
  ловит отступление от него. Решение без проверки — пожелание.
- Поля решения: «Статус» (`принято`, `заменено D-NN`, `отклонено`),
  «Дата» (ISO), «Решение», «Почему», «Проверка»; по необходимости —
  «Метка» (машинная отметка, на которую ссылаются критерии этапов,
  `docs/direction/ROADMAP/README.md`).
- Решения других репозиториев пишутся с префиксом репозитория
  (`Galdhold:Р12`, `DPpass:D-24`), чтобы не путаться с номерами этого
  журнала.

Решения D-01…D-11 приняты **2026-10-04** по постановке автора при
создании репозитория (этап 0); следующие — по ходу этапов, у каждого
своя дата.

## Принятые

### D-01 — Назначение: система живой документации, а не книга

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Репозиторий хранит проверяемую историю пути автора
  (dpsmpx) и его проектов: источники, атомарные факты, хронологию,
  выводы с привязкой к фактам и структуру будущей книги о методе
  AI-assisted разработки. Книга здесь сейчас не пишется.
- **Почему.** Книга о методе имеет смысл только на проверяемой
  фактической базе; база копится раньше текста.
- **Проверка.** `tools/verify/check_book_gate.py` — в `docs/book/` нет
  прозы и черновиков глав.

### D-02 — Шлюз книги: выпуск VoxelRPG в Steam и отдельное решение

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Черновики глав и проза книги запрещены, пока не выполнены
  оба условия:
  1. есть активный факт с меткой `steam-release` о выпуске VoxelRPG
     (D-03) в Steam: `basis: observed`, `source_type: url`, адрес —
     страница игры в магазине Steam (`store.steampowered.com`);
  2. принято отдельное решение с меткой `book-permission`, которое
     ссылается на этот факт по номеру.

  «Выпуск в Steam» — игра продаётся или устанавливается как продукт
  со своей страницы в магазине Steam, включая ранний доступ. Страница
  «Coming Soon», Steam Playtest, демо и участие в Next Fest выпуском не
  считаются. Это определение меняется только новым решением.
- **Почему.** Так поставлено автором: книга о методе пишется после
  внешнего результата, а не до него. Ранний доступ включён, потому что
  он записан в Galdhold как возможный формат выпуска (F-0026).
- **Проверка.** `tools/verify/check_book_gate.py`; этап 5 —
  `tools/verify/check_stages.py`.

### D-03 — Что такое VoxelRPG в этом репозитории

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** VoxelRPG — игра из репозитория `dpsmpx/Galdhold`
  (прежнее имя `3D_Voxel_OpenWorld_RPG`, F-0030), с 2026-10-04
  называемая Galdhold (F-0029). Тег проекта — `voxelrpg`; технология
  движка в том же репозитории — тег `engine`. Шлюз D-02 относится к
  этой игре под любым её названием.
- **Почему.** Название и имя репозитория сменились 2026-10-04; тег,
  привязанный к имени, сломался бы при следующем переименовании.
- **Проверка.** `tools/verify/check_facts.py` — теги проектов фактов
  берутся только из таблицы `docs/direction/SCOPE.md`.

### D-04 — Модель данных: один факт — один файл, узкая схема

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Факт — файл `docs/facts/F-NNNN.md` только из front matter;
  вывод — `docs/insights/I-NNNN.md`, гипотеза — `docs/insights/H-NNNN.md`.
  Front matter — узкое подмножество YAML: строки `ключ: значение` и
  списки `[a, b]` в одну строку; без вложенности, кавычек и многострочных
  значений. Поля и допустимые значения — `docs/facts/README.md` и
  `docs/insights/README.md`. Даты — ISO `YYYY-MM-DD`. Номера стабильны
  и не переиспользуются: источник `S-NN`, заметка `N-NNNN`, факт
  `F-NNNN`, вывод `I-NNNN`, гипотеза `H-NNNN`, решение `D-NN`.
- **Почему.** Узкую схему можно проверить полностью и без зависимостей;
  лишняя гибкость формата — место для непроверяемых утверждений.
- **Проверка.** `tools/verify/check_facts.py`, `tools/verify/check_insights.py`.

### D-05 — Источники: реестр, привязка к коммиту, без копирования

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Каждый факт ссылается на источник из реестра
  `docs/sources/REGISTRY.md` и на точное место в нём: коммит, файл на
  коммите (`путь@sha`), релиз (`тег@sha`), адрес страницы с датой
  наблюдения или заметку `N-NNNN` с происхождением
  (`docs/sources/CITATION.md`). Из других репозиториев сюда попадают
  только идентификаторы и краткие выжимки (формулировка факта — не
  длиннее 300 знаков); код, большие фрагменты документов и
  архитектурные описания не копируются.
- **Почему.** Утверждение без точного места проверить нельзя. Часть
  источников — закрытые репозитории автора (у Galdhold — по
  `Galdhold:Р12`, F-0024): их содержимое не выносится даже в закрытый
  репозиторий сверх необходимого для ссылки.
- **Проверка.** `tools/verify/check_facts.py` (форма ссылок, длина),
  `tools/verify/check_registry.py`, `tools/verify/check_refs.py`
  (сверка с клонами источников в полном прогоне).

### D-06 — Факты не переписываются

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Однажды закоммиченный факт не удаляется, а его ядро
  (`id`, `kind`, `date`, `statement`, `area`, `projects`, `basis`,
  `source`, `source_type`, `ref`, `observed`, `refines`, `marks`) не
  меняется. Уточнение — новый факт с `refines: F-NNNN`. Ошибка — новый
  факт, а старый получает `status: superseded`, `superseded_by: F-NNNN`
  и `revised_by: D-NN` — отдельное решение, объясняющее замену.
- **Почему.** История, которую можно молча переписать, не проверяема.
- **Проверка.** `tools/verify/check_history.py` — сравнивает каждый факт
  с его первой закоммиченной версией.

### D-07 — Факт, вывод и гипотеза разделены

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Факт — без интерпретаций и оценок. Вывод (`kind: insight`)
  ссылается на один или несколько активных фактов и имеет уровень:
  `observed` (наблюдаемый — прямо следует из фактов) или `bounded`
  (ограниченный — с обязательным полем `limits`, где сказано, чего он
  не утверждает). Гипотеза (`kind: hypothesis`) — спорный вывод; у неё
  обязательное поле `test` — какой будущий факт её подтвердит или
  опровергнет. Предписания («делай так») в описании метода запрещены,
  пока для них нет решения.
- **Почему.** Смешение фактов и толкований — главный способ
  приукрасить историю, не солгав ни в одном отдельном утверждении.
- **Проверка.** `tools/verify/check_insights.py`,
  `tools/verify/check_forbidden.py` (оценочные слова, маркеры вывода в
  фактах, предписания в методе — `tools/verify/forbidden_claims.txt`).

### D-08 — Проверки — часть завершения; в сессии, без GitHub Actions

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Перед каждым коммитом — `tools/verify/run.sh --quick`,
  перед вливанием в `main` — `tools/verify/run.sh --full` (с клонами
  источников и самопроверкой). Изменение структуры документов и
  проверки к нему — в одном коммите. GitHub Actions не используются:
  проверки запускаются в сессии.
- **Почему.** Так устроены проверки в других репозиториях автора
  (F-0027, F-0039). Самопроверка нужна, чтобы проверки не оказались
  молча пропускающими: каждая доказанно падает на испорченной копии.
- **Проверка.** `tools/verify/selftest.py`.

### D-09 — Этапы — по зрелости репозитория, с машинными критериями

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** `docs/direction/ROADMAP/` описывает этапы зрелости этой
  системы документации, а не этапы написания книги. У каждого критерия
  выхода есть машинное условие (`<!-- gate: … -->`); где нужно суждение
  автора, условие — принятое решение с меткой. Этап выполнен, только
  когда отмечены все критерии, а отметка `[x]` при ложном условии —
  ошибка.
- **Почему.** Критерий, который нельзя проверить, превращает план в
  пожелания.
- **Проверка.** `tools/verify/check_stages.py`,
  `tools/verify/check_consistency.py`.

### D-10 — Статус в README строит скрипт

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Блок состояния в `README.md` между метками
  `status:begin` и `status:end` строит `tools/verify/readme_status.py
  --write` из ROADMAP, STATUS книги и счёта документов; руками не
  правится. Остальной README меняется вручную.
- **Почему.** Прогресс, написанный руками, расходится с документами.
- **Проверка.** `tools/verify/readme_status.py` — без `--write` сверяет
  блок с документами.

### D-11 — Язык документов — русский, поля — латиницей

- **Статус:** принято
- **Дата:** 2026-10-04
- **Решение.** Текст документов — по-русски, как в репозиториях автора.
  Имена полей, значения перечислений, теги проектов и номера —
  латиницей.
- **Почему.** Источники в основном русскоязычные; машинные поля
  проверяются точным совпадением.
- **Проверка.** `tools/verify/check_facts.py`,
  `tools/verify/check_insights.py` — неизвестные поля и значения
  отклоняются.

### D-13 — Состав предмета: остальные публичные репозитории автора

- **Статус:** принято
- **Дата:** 2026-10-04
- **Метка:** `scope-prior-review`
- **Решение.** Из публичных репозиториев автора, которых не было в
  реестре (N-0004), в предмет под тегом `prior` входят DP_Ecosystem,
  DP_Repeated_Tasks, PixRogue, DP_TextFile_Sorter, dpcalls,
  DP_Autoclicker, DP_Typing_Master, DP_Backup_Tool, DP_Gen_Bots,
  DP_Graph_Builder (S-12…S-21) и форк andors-trail-load (S-22). Из

  pascalabcnet в предмет не входят. Закрытые репозитории автора вне

- **Почему.** Выбор автора в сессии Claude Code 2026-10-04 (форма
  вопросов по группам репозиториев). Тег `prior` уже обозначает
  публичные проекты автора как контекст траектории — новый тег не

  «предыдущих» проектов на публичные проекты вне остальных тегов,
  потому что часть включённых начата одновременно с VoxelRPG
  (F-0061, F-0062). Форк в основном состоит из чужой истории, поэтому
  граница проведена по коммитам автора; чужой код не копируется (D-05).
- **Проверка.** `tools/verify/check_registry.py` — источники тега
  `prior` есть в реестре; `tools/verify/check_refs.py` — факты о первых
  коммитах сверены с клонами; `tools/verify/check_stages.py` — критерий
  `decision-mark:scope-prior-review` этапа 2.

### D-16 — Репозиторий — подсистема DPmetaApp, каталог `dpprofile/`

- **Статус:** принято
- **Дата:** 2026-10-25
- **Решение.** С 2026-10-25 DPprofile живёт в репозитории DPmetaApp, в
  каталоге `dpprofile/`: документы, проверки и история перенесены
  слиянием поддерева (`main` `3e76c10`). Репозиторий DPprofile заморожен:
  работа там не начинается, архивирует его автор. Свой процесс
  сохраняется: решения — этот журнал (извне — `DPprofile:D-NN`), правила —
  `CLAUDE.md`, проверки — `tools/verify/` из каталога `dpprofile/`; пути —
  от `dpprofile/`. Своей вершины git у каталога нет, поэтому история для
  проверок (`check_history.py`, источник `self` в `check_refs.py`,
  устойчивость файла в критериях этапов) — два отрезка
  (`docmodel.history`): прежний `main` (пути от корня) и коммиты DPmetaApp
  после слияния поддерева (пути с `dpprofile/`); основная история
  DPmetaApp в неё не попадает, источник `self` — только эти коммиты.
- **Почему.** Ответы автора 2026-10-25 в опросе сессии DPmetaApp
  (`DPmetaApp:D-43`): DPprofile переезжает в DPmetaApp «только как
  подкаталоги со своими сборщиками, README и прочим», по одной системе за
  раз с проверками; в старом репозитории — надпись, что его нужно
  архивировать.
- **Проверка.** `tools/verify/check_history.py --strict` из `dpprofile/` —
  история фактов и решений не пропущена; `tools/verify/selftest.py` —
  случаи «каталог в чужом репозитории»: чистая история проходит;
  переписанный факт ловится, и после удаления и возврата каталога тоже;
  коммит внешнего репозитория источником `self` не принимается.

### D-18 — Перенос в SocialMediaImage с сохранением истории

- **Статус:** принято
- **Дата:** 2026-11-11
- **Решение.** Во исполнение D-17 актуальное дерево перенесено из
  DPmetaApp в `dpprofile/` SocialMediaImage. Проверяемая история — два
  отрезка: объединённая самостоятельная линия DPprofile с исходной
  историей и изменениями периода DPmetaApp, затем путь компонента в
  SocialMediaImage. Опора первого отрезка —
  `0e17def1899b6ba76cbbeabb8eeee07f1b103da0` (tree экспортированной версии,
  родители — исходный main DPprofile и экспорт). Опора — второй
  родитель импорта поддерева. Содержимое фактов не меняется.
