# Управление контентом

Кто публикует, что требует одобрения, что можно автоматически, как
отменяется публикация, кто отвечает за факты и за визуальное качество,
что и сколько хранится (постановка §62–64, §86–88; Д12, Д26, Д29, Д30).
Политика в данных — `data/policy/publication.yaml`.

## 1. Роли

| Роль | Может | Кто |
|---|---|---|
| Reader | читать всё в репозитории | автор, сессия ИИ, инструменты |
| Editor | писать каноны, варианты, данные (факты — с источником) | автор, сессия ИИ |
| Reviewer | критика, проверки, оценки | автор, сессия ИИ (отдельным проходом — `QUALITY_MODEL.md`, §4) |
| Publisher | одобрять версии и запускать рабочую публикацию | **только автор** |
| Admin | менять решения, политику, адресаты, учётные данные | **только автор** |

Сессия ИИ — роли **Generator и Reviewer** (§87): черновики, адаптации,
критика, пакет публикации, пробный прогон и имитации. Она **не
одобряет**, **не держит рабочих токенов** и **не публикует** в рабочие и
тестовые адресаты (`session_modes: [dry-run, development]`). Агенты
(исследование, редактура, проверка фактов, визуал, адаптация,
аналитика) — так же: `AI → draft → review → propose`, затем `автор →
approve`, `publisher → publish` (§86). Инструменты отказывают в
одобрении и рабочей публикации, если видят сессию Claude Code (Д26);
настоящая граница — у сессии нет токенов. Исключение (Д36): **выгрузку
сайта** может запустить локальная сессия Claude Code на машине автора
после его «да» на каждую команду (`local_session_production: [website]`);
облачная — никогда; одобрение — по-прежнему только автор.

## 2. Что требует одобрения

| Что | Одобрение | Как |
|---|---|---|
| Любая рабочая публикация (сайт, площадки) | **да, автор** | `approve` записывает sha256 содержимого варианта; изменённое — не публикуется (Д12) |
| Публикация в безопасном режиме (тестовый канал, staging) | нет | проверки валидатора обязательны |
| Изображение с портретом | да, автор (гейт Brand, Д18) | `approval` объекта |
| Факты в реестре | нет отдельного — источник и дата обязательны (Д6) | `CLAIM_POLICY.md`, §6 |
| Решения, позиционирование, идентичность, роли площадок, визуальный язык | да, автор | `DECISIONS.md`, «Изменение основ» (`PROCESS.md`, §4) |
| Смена стратегии по метрикам | да, автор (§62) | рекомендация — `INTERPRETATION`, решение — правка `DECISIONS.md` |

## 3. Автоматическая публикация

Сейчас — **ни для одного класса** (`auto_publish_classes: []`, Д12).
Класс добавляется только решением в `DECISIONS.md` с доказанным
правилом: какой контент (например, «запись журнала изменений открытого
репозитория из одобренного шаблона без свободного текста»), на какую
площадку, какие проверки заменяют одобрение каждой версии, как
откатить. До такого решения движок требует одобрение для production.

## 4. Отмена и исправление публикации

| Ситуация | Что делать |
|---|---|
| Ошибка в тексте опубликованного | новая версия варианта → `seal` → одобрение → `publish` (политика `on_update: edit` — правка поста; старая запись `SUPERSEDED`) |
| Пост нужно убрать | автор удаляет на площадке (Telegram — бот может удалить только посты младше 48 часов) или командой `publish --delete PUB-… --production` (адаптер удаляет и пишет `DELETED`); на сайте запись снимается сборкой без неё, а журнал и Git сохраняют историю |
| Запланированное не нужно | `publish --cancel PUB-… --production` — событие `CANCELLED` до наступления времени |
| Исход неизвестен | сверка: `publish --reconcile PUB-… --exists yes|no` |
| Опубликовано не туда | удалить на площадке, `DELETED` в журнал, находка — в `TODO.md` и разбор адресатов (`destinations`) |

Журнал не правится руками: исправление — новым событием.

## 5. Хранение (§64)

| Что | Сколько | Почему |
|---|---|---|
| Журнал публикаций (`data/publications/*.jsonl`) | **всегда, неизменяем** | история публикаций — собственность автора (§122) |
| Зафиксированные версии канона, одобрения, `provenance.yaml` | **всегда, неизменяемы** | цепочка «факты → канон → правки → вариант → публикация» (§89) |
| Отклонённые варианты, их спецификации и рендеры | в Git, без срока | история выбора (Д14); не публикуются |
| Черновики объектов и вариантов | в Git, пока объект не `REJECTED`/`ARCHIVED`; после — остаются как история | восстановление решений |
| Опубликованное устаревшее | не переписывается; помечается проверкой `stale` | что было опубликовано — история |
| Медиа | экспорт утверждённого — в Git; мастер-видео — вне Git в резервной копии автора | Git не для больших файлов |
| Кэш генерации, логи, сборки (каталог сборки build, не в Git) | 30 и 90 дней, можно удалять | восстанавливаются |
| Сырые выгрузки метрик | у автора, вне Git (`docs/SECURITY.md`, §5) | личные данные зрителей |

Удалять можно только восстановимое (сборки, кэш, логи). Удаление
записи из Git (секрет, личное) — по `docs/SECURITY.md`, §4, решение автора.

## 6. Ответственность

| За что | Кто | Чем подтверждается |
|---|---|---|
| Факты (`facts.yaml`) | сессия вносит с источником и датой; автор подтверждает спорное | проверки `facts`, `claims`; `recheck_by` |
| Канон и варианты | сессия пишет, валидатор проверяет, автор одобряет | `canonical seal`, `variant seal`, `approve` |
| Визуальное качество | сессия — по чек-листу критики и проверкам `visual`/`exports`; автор — гейт Brand | `QUALITY_MODEL.md` |
| Права и происхождение | сессия записывает; автор подтверждает права третьих лиц | `provenance`, `RIGHTS_MATRIX.md` |
| Адресаты и учётные данные | автор | `destinations`, `health` |
| Публикация | автор | журнал с `approval` |

## 7. След изменений (§88)

Кто, что, когда, откуда, какая версия: Git (автор коммита и PR),
`history` объекта, `generation` и `trust` в канонах и вариантах,
`approval` с датой и sha256, `actor` и `mode` в журнале публикаций,
`provenance.yaml` медиа. Всё это — в репозитории и в выгрузке `bundle`.
