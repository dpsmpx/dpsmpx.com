# Процесс

Зачем каждое правило `CLAUDE.md`, откуда оно и как устроена работа
сессии. Над этим файлом — `docs/direction/DECISIONS.md` (Д0: иерархия
`DECISIONS.md` → `CLAUDE.md` → остальное). Инструменты —
`docs/ARCHITECTURE.md`.

## 1. Откуда правила

Культура работы взята из закрытых проектов автора, где она уже
работает (Д0): записанные решения с историей, «готово — остановиться»,
PR сразу после первого пуша, TODO только для хвостов, аудиты на дату,
проверки в сессии без Actions (Д3). Предмет — свой: контент, идентичность,
площадки.

## 2. Сессия

1. **Начало.** Хук `.claude/hooks/session-start.sh` печатает указатель
   на `docs/session/HANDOFF.md` и ветки с невлитой работой. Если задача
   начата на ветке — продолжать с неё. Затем
   `docs/context/AUTHOR_MASTER_CONTEXT.md`, под задачу — `DECISIONS.md`,
   `TODO.md`.
2. **Сверка запроса.** Запрос автора — высший приоритет, но до работы
   сверяется с решениями: расхождение — вопрос с вариантами, а не тихое
   исполнение или «исправление». Деталь, меняющая то, что увидит
   аудитория (имя, лицо, факты, площадка, деньги, право), — вопрос;
   мелочи сессия решает сама и называет в отчёте.
3. **Работа.** Коммит и пуш — после каждого законченного куска и не
   реже раза в полчаса (`WIP:` — для незаконченного). Первый пуш —
   сразу черновой PR с «сделано / осталось», обновляемым с каждым
   пушем.
4. **Конец.** `tools/check.sh` зелёный (или красное названо в PR);
   `HANDOFF.md` обновлён; хвосты — в `TODO.md`; решения — в
   `DECISIONS.md`.

**Границы задачи** (§98). У каждой задачи — объявленные границы: id в
`ROADMAP/ROADMAP.md` или поручение автора. Всё постороннее в диффе —
убрать, объяснить в описании PR или вынести отдельной задачей в
ROADMAP/TODO. Порядок инженерной работы (§97): задача → ветка →
реализация → точечные проверки → коммит → пуш → PR (черновиком сразу
после первого пуша) → ревью → полная проверка → слияние.

**Почему так.** Сессия ИИ может закончиться в любой момент (лимит
контекста, обрыв). Всё, что не в Git, теряется; всё, что в Git без
HANDOFF и PR, придётся восстанавливать заново.

## 3. Почему правила такие

| Правило (`CLAUDE.md`) | Почему |
|---|---|
| Нет объекта — нет контента | Цель, аудитория и площадка задаются до работы; иначе вариант выбирают по вкусу (Д1, Д14). |
| Порядок конвейера не меняется | Генерация без брифа даёт «красиво, но не о том»; публикация без `APPROVED` — необратимая ошибка (Д12). |
| Неизвестное не придумывать | Догадка о человеке, попавшая в публичный образ, — ложь от его имени. `ACCESS = LIMITED` честнее. |
| Факты — только из реестра | Числа и состояния меняются; реестр хранит дату и источник, контент — ссылку (Д6). |
| Оценка ИИ — не доказательство | Аудит канала: посты-оценки не получили ни одной реакции (Д7). |
| Идентичность не меняется молча | Публичный образ согласован между площадками; тихая правка расходится с остальными (§4). |
| Автор — только `dpsmpx`, имени нет нигде (Д40); образ — только с фото | Необратимые решения о личном принимает только автор (Д10, Д18, Д40). |
| Закрытые проекты — только фактами | Galdhold Р12 и лицензия DPlang (Д17). |
| Публикуется только одобренная автором версия; токены — только у автора | Ошибка публикации необратима; учётные данные — главный риск; одобрение по хэшу не даёт опубликовать изменённое (Д12, Д26). |
| Адресат — только по явным id | Личный канал вместо проектного или рабочий вместо тестового — необратимо (Д25). |
| Текст площадки — из канона, числа — подстановкой | Иначе пять копий расходятся, а смена факта не находит производное (Д22, Д28). |
| Секретов в Git нет | Репозиторий закрыт, но не сейф; поиск секретов GitHub здесь не работает (Д3, `docs/SECURITY.md`). |
| `tools/check.sh` перед коммитом | Единственный контроль качества без Actions (Д3). |
| Готово — остановиться | Следующая задача без поручения тратит время автора на ревью ненужного. |

## 4. Изменение основ

**Основы** — то, на чём держится согласованность публичного образа:
имя и псевдоним, позиционирование (Д4), визуальный язык и токены (Д9,
`assets/brand/tokens.json`), аудитории и опоры
(`CONTENT_STRATEGY.md`, §2–3), роли площадок (§6), политика
утверждений (Д6, Д7), иерархия проектов (Д5).

Порядок:

1. **Согласие автора.** Сессия предлагает изменение с причиной и
   вариантами; решает автор.
2. **Решение.** Правка в `DECISIONS.md` (новое Д или правка старого) и
   запись в истории (§4 там) — с датой и причиной.
3. **Документы.** Обновить всё, что выводится из решения: стратегию,
   идентичность, визуальную систему, модели площадок, мастер-контекст.
   Токены бренда — вместе с хэшем A-003 в `data/provenance/assets.yaml`
   (иначе проверка `provenance` красная — это намеренно).
4. **Шаблоны и объекты.** Проверить `templates/`, `prompts/` и все
   объекты в состояниях от `BRIEFED` до `EXPORTED`: что затронуто —
   вернуть на ревизию с записью в истории. Опубликованное не
   переписывается — это история.
5. **Проверки.** `tools/check.sh`; итог — в PR.

## 5. Проверки

Состав и устройство — `docs/ARCHITECTURE.md`, §6. Уровни (постановка
§99): `--quick` (схемы, объекты, секреты, ссылки, адресаты, матрица —
секунды) — по ходу работы; `--affected` (проверки по изменённым файлам,
тесты — если менялся код) — перед коммитом куска; полный — перед
«готово» и PR; `--release` (полный + production-сборка сайта + сводки
кампаний) — перед рабочей публикацией. Красная проверка —
не повод снимать её: найти причину в данных; если права проверка —
исправить данные, если неправа — исправить проверку и добавить тест.
Записанный гейт `pass` при красной проверке — ошибка, а не
«потом поправим».

## 6. Вопросы автору и ожидание

- Объект, ждущий автора, — `blocked_by` в `item.yaml`, строка в
  `TODO.md` («за автором») и в `HANDOFF.md`.
- Открытые решения — только в `DECISIONS.md`, §3, с правилом до
  решения; сессия не принимает их сама.
- Профили на площадках меняет автор: сессия готовит текст и
  напоминает (`IDENTITY_CONFLICTS.md`).

## 7. Аудиты

`docs/audits/` — срезы на дату: что было видно и как получено. Задним
числом не переписываются; новое — новым срезом или датированным
дополнением отдельным файлом. Битая ссылка в аудите — предупреждение,
а не ошибка проверки `links`.
