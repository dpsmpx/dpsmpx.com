# Восстановление после сбоев

Сценарии §66, §67, §108–109 и решение Д30. Принцип: ни одна площадка,
сайт или провайдер ИИ не единственное место хранения канона; история
публикаций — в журнале в Git.

| Сценарий | Что потеряно | Восстановление | Что продолжает работать |
|---|---|---|---|
| **Сайт потерян** (хостинг закрыт, аккаунт заблокирован) | раздача страниц | новый хостинг — новым решением по Д35 (выгрузка командами системы); до него загружается только содержимое `build/site/production/` после `python3 -m tools.cs site build --env production`, не корень репозитория; DNS домена → новый хостинг (ОР-11: домен у автора, не у хостинга) | всё содержимое — в Git; публикации на площадках идут, если канон в Git (политика `outage`) |
| **На хостинг выгружено не то** (весь репозиторий, чужой каталог — скриптом в обход системы) | закрытость (Д2): всё, что лежало в `public_html/`, могли прочитать | убрать источник (ярлык, скрипт); `git pull`; `python3 -m tools.cs site deploy --dry-run`, затем `site deploy` — свежая сборка с проверками, `--delete` уберёт лишнее, `/.well-known/` под защитой (выпуск закрыт, `live: false`, — очистить `public_html/` в файловом менеджере панели). Не ручным rsync. Доказательство — `site deploy --dry-run`: «изменений: 0», и полный список файлов на сервере (`find . -mindepth 1` в каталоге сайта) совпадает со списком сборки: `/.well-known/` и каталоги `.~tmp~` пробный прогон не показывает (`docs/audits/2026-10-05-SITE_LEAK_INCIDENT.md`, §6). Оценка утечки — `docs/SECURITY.md`, §6 | канон и Git; другие площадки |
| **Репозиторий потерян** (GitHub недоступен, аккаунт) | удалённая копия | локальный клон автора → новый удалённый репозиторий; без клона — последний архив `bundle` (`BACKUP.md`) | работа офлайн по локальной копии |
| **Учётные данные потеряны или украдены** | доступ к площадке | `CREDENTIALS.md`, §3: отозвать, выпустить новые, `health --remote` | остальные площадки и сайт |
| **API площадки изменился** | адаптер | ошибки `UNKNOWN_PLATFORM_ERROR`/`INVALID_CONTENT` в журнале; обновить `capabilities.yaml` и адаптер этой площадки; модель, кампании, сайт не меняются (§69); до починки — ручной путь (Д33) | все остальные площадки |
| **Площадка временно недоступна** | ничего | публикации `FAILED (retryable)` → `publish --due` позже (§67) | канон, сайт, другие площадки |
| **Площадка закрылась или удалила записи** | производные на площадке | сайт и журнал хранят оригинал и адреса (Д21, §25); новая площадка — новый адаптер | всё остальное |
| **Провайдер ИИ недоступен** | генерация | объекты остаются черновиками (§108); ядро — офлайн-первым: факты, правка, версии, предпросмотр, сборка сайта работают без ИИ | всё, кроме генерации |
| **Медиа потеряны** (файл испорчен) | файлы | Git хранит каждый файл; хэши в `provenance.yaml` и `assets.yaml` ловят порчу (`provenance`); экспорт пересобирается из спецификации (рендер детерминирован, Д11); мастер-видео — из внешней копии | остальное |
| **Данные испорчены** (битый YAML, журнал) | согласованность | `tools/check.sh` называет файл и строку; откат правки через Git (`git log -p`, `git revert`); журнал — только дописывание, исправление — новым событием | — |
| **Исход публикации неизвестен** (обрыв) | знание, вышел ли пост | `publish --reconcile PUB-… --exists yes|no` после проверки на площадке (Д24) | всё |

## Порядок действий при любом сбое

1. `python3 -m tools.cs health` — что именно сломано.
2. Канон и журнал целы? (`git status`, `tools/check.sh canonical publications`).
3. Остановить рабочие публикации затронутой площадки (не запускать
   `--production` для неё), остальные — по плану.
4. Починить по таблице; записать находку в `TODO.md`, решение — в
   `DECISIONS.md`, если меняется правило.
