# Сайт автора: архитектура, публикация, SEO

**Вопрос.** Как устроить собственный сайт автора — центральную точку
публикации и архив (Д21): на чём строить, где держать, какие фиды и
метаданные нужны, чтобы сайт был простым, переносимым, дешёвым, под
версионным контролем и не зависел от соцсетей (`PLATFORM_VISION.md`,
§2, §4–7, §25, §32–35, §48, §79–85).

**Источники** прочитаны 4 октября 2026: indieweb.org/POSSE; ogp.me;
sitemaps.org/protocol.html; rfc-editor.org/rfc/rfc4287 (Atom);
rssboard.org/rss-specification (RSS 2.0); jsonfeed.org/version/1.1;
developers.google.com/search/docs (canonical, «Article» structured
data); developers.cloudflare.com/pages/platform/limits;
docs.github.com/en/pages (что такое Pages, лимиты); gohugo.io (Hugo
v0.167.0); decapcms.org/docs/intro. Это исследование; решение — Д32.

---

## 1. Практика «сначала свой сайт»

**POSSE** — «Publish (on your) Own Site, Syndicate Elsewhere»: запись
сначала публикуется на своём сайте, затем копии или ссылки уходят на
площадки — со ссылкой на оригинал (IndieWeb). Это ровно модель Д21:

- у каждой записи **одна каноническая ссылка** на своём домене;
- версии на площадках — производные (Д22) и ссылаются на оригинал;
- если площадка удалит запись или сменит правила, оригинал и история
  остаются на сайте и в Git;
- домен — часть идентичности: хостинг меняется, адреса — нет.

## 2. Три архитектуры (§32)

| | **A. Статический сайт + генератор** | **B. Headless CMS + фронтенд** | **C. Свой бэкенд + фронтенд** |
|---|---|---|---|
| Как | генератор собирает HTML из файлов в Git; хостинг раздаёт файлы | контент в CMS (Git-based — Decap; API-based — Sanity, Contentful, Strapi), фронтенд забирает его при сборке или запросе | сервер приложения + база + шаблоны/SPA |
| Сложность | низкая | средняя–высокая (ещё одна система, вход, схема контента CMS) | высокая |
| Сопровождение | обновления генератора | обновления CMS, интеграции, доступы | сервер, ОС, база, резервные копии, патчи |
| Стоимость | хостинг статики — бесплатный тариф; домен | облачные CMS — тарифы по объёму; самохостинг — сервер | сервер постоянно |
| Хостинг | любой статический (CDN) | статика + CMS | VPS/PaaS |
| Скорость | максимальная (готовые файлы на CDN) | высокая при сборке, ниже при запросах | зависит от сервера |
| Безопасность | поверхность атаки минимальна: нет кода на сервере и базы | вход в CMS, токены API | всё приложение — поверхность атаки |
| Расширяемость | динамика — через внешние сервисы или функции на краю | высокая для редакторов | любая |
| Автоматизация | сборка из Git — тривиально | вебхуки CMS | любая, но своя |
| Переносимость | максимальная: папка файлов | у API-CMS контент вне Git — зависимость от вендора; Decap хранит в Git | данные в своей базе — переносимы с усилием |

**Вывод.** Задачу Д21 (визитка, проекты, новости, архив, фиды) решает
**A**. B даёт веб-редактор, но у API-CMS источник истины уходит из Git
(против Д1 и §109), а Decap (Git-based) добавляет зависимость от входа
через GitHub без выигрыша для одного автора, который работает через
репозиторий. C — то, от чего постановка предостерегает (§32, §33):
сервер и база ради возможностей, которые сейчас не нужны.
**Гибрид** (статика + функции на краю у хостинга) — допустимое
расширение позже: приём вебхуков, форма, поиск на сервере.

## 3. Генератор: готовый или свой

| Вариант | За | Против |
|---|---|---|
| Hugo (v0.167.0), Zola — один бинарник | быстрые, зрелые, темы | второй набор инструментов в сессии; данные модели (факты, варианты, журнал публикаций) пришлось бы дублировать в форматы генератора; проверка фактов и устаревания всё равно в Python — две логики вывода |
| Astro, Eleventy — Node | гибкие компоненты | зависимости npm и сборщик ради нескольких страниц |
| **Свой генератор в `tools/cs`** (Python, без новых зависимостей) | одна модель и одни проверки: сайт строится из тех же объектов, фактов и журнала, что и публикации; детерминированные тесты; выход — обычные файлы | шаблоны и разметку сопровождаем сами |

**Вывод.** Свой небольшой генератор в существующем пакете (`tools/cs/site/`):
сайт — это ещё один «адаптер» той же модели. Выход — статические
файлы, поэтому переход на Hugo/Astro позже — работа над шаблонами, а
не над данными.

## 4. Хостинг для `dpsmpx.com` (ОР-11)

| | Cloudflare Pages | GitHub Pages | Netlify |
|---|---|---|---|
| Цена | бесплатный тариф | бесплатно **только для публичных** репозиториев | бесплатный тариф (условия тарифа в этой сессии не перепроверены) |
| Лимиты (бесплатно) | 500 сборок в месяц, 1 сборка одновременно, **20 000 файлов**, **25 МиБ на файл** | рекомендованный предел 1 ГБ; «не для коммерческого хостинга»; один сайт пользователя на аккаунт | — |
| Свой домен | да | да | да |
| Без Actions (Д3) | загрузка готовой папки с машины автора (Direct Upload) | сборка Pages идёт на стороне GitHub; репозиторий собранного сайта — отдельный публичный | загрузка папки CLI |
| Предпросмотр | превью-развёртывания на отдельных адресах | нет | превью-развёртывания |

**Вывод для ОР-11.** Рекомендация — **Cloudflare Pages с загрузкой
готовой сборки** (исходники остаются закрытыми, Actions не нужны,
есть превью для staging). Домен регистрирует автор у любого
регистратора; стоимость — по прайсу регистратора на дату покупки (в
сессии не проверялась). Хостинг заменяем: сайт — папка файлов.

## 5. Структура и адреса (§5, §79)

Канонический адрес — стабилен и не зависит от площадок; меняется
только по решению, со старого адреса — перенаправление.

```
/                         главная (RU)            /en/            главная (EN)
/about/                   обо мне                 /en/about/
/projects/                проекты                 /en/projects/
/projects/<id>/           страница проекта        /en/projects/<id>/
/news/                    лента записей (новости, дневник, статьи, релизы — категории)
/news/<slug>/             запись (slug не меняется после публикации)
/tags/<tag>/              записи по метке (когда записей больше нескольких)
/feed.xml  /rss.xml  /feed.json   фиды
/sitemap.xml  /robots.txt
/api/v1/…                 статические JSON (проекты, записи) — для своих клиентов
```

- Разделы «devlog», «articles», «releases», «media», «downloads» из
  предварительной схемы (§5) **не отдельные ветки адресов, а категории
  одной ленты** `/news/`: при малом числе записей пустые разделы
  выглядят заброшенными, а адрес записи не должен зависеть от того, в
  какой раздел её отнесли. Отдельная страница раздела появится, когда
  в категории будет что показать.
- «Контакт» — блок на главной и в «обо мне», а не отдельная страница.
- Английский — для главной, «обо мне» и проектов (Д21), с
  `hreflang`-парами; записи — на русском.

## 6. Фиды (§34)

| Формат | Зачем | Источник |
|---|---|---|
| **Atom 1.0** (`/feed.xml`) | строгий: обязательные `id` и `updated` — устойчив к правкам записей | RFC 4287 |
| **RSS 2.0** (`/rss.xml`) | самый распространённый у читалок и сервисов рассылки | rssboard.org |
| **JSON Feed 1.1** (`/feed.json`) | своим клиентам (бот Discord, рассылка, приложение) — JSON без парсера XML | jsonfeed.org/version/1.1 |

Все три строятся из одного списка записей — стоимость поддержки
одинакова; `id` записи = её канонический адрес и не меняется.

## 7. SEO и вид в соцсетях (§81–82)

Только необходимое:

- `<title>` и `meta description` у каждой страницы;
- `<link rel="canonical">` — абсолютный адрес на `dpsmpx.com`
  (Google: canonical — сильный сигнал, но не приказ; согласованность
  адресов во внутренних ссылках, sitemap и canonical);
- `hreflang` для пар RU/EN (+ `x-default`);
- **Open Graph**: обязательные `og:title`, `og:type`, `og:image`,
  `og:url` (ogp.me), плюс `og:description`, `og:locale`; карточка
  `twitter:card = summary_large_image`. Размер изображения OG 1200×630 —
  распространённая рекомендация площадок; официального размера в
  протоколе нет → формат `og_image` с `verified: false` (Д13);
- **структурированные данные** (JSON-LD): `Person` — главная и «обо
  мне»; `WebSite`; `BlogPosting`/`NewsArticle` — записи (Google:
  «Article» structured data). Без оценок и отзывов — их нет;
- `/sitemap.xml` (≤ 50 000 адресов и 50 МБ на файл); `/robots.txt`;
- **staging закрыт от индексации**: `Disallow: /` и `noindex` на каждой
  странице.

## 8. Остальное из §2

| Тема | Вывод |
|---|---|
| **Поиск** | при малом числе записей не нужен; позже — индекс JSON при сборке и поиск в браузере (без сервера) |
| **Архив** | лента по годам + постоянные адреса; удалённое с площадок остаётся на сайте (Д21) |
| **Метки** | из модели (`tags`), страницы меток — когда записей с меткой ≥ 2 |
| **Страницы проектов** | из сущности проекта (`data/projects/`) и фактов реестра — без ручного переписывания чисел (§22) |
| **Журнал изменений** | релизы — из `data/releases/` (когда будут); у закрытых проектов — по фактам, без сырых данных GitHub (§37) |
| **Медиа** | изображения — в Git (сотни КБ); видео — не в Git: хост — YouTube, мастер-файлы — в резервной копии автора (`docs/operations/BACKUP.md`); у Cloudflare Pages предел 25 МиБ на файл |
| **Рассылка** (§84) | точка расширения — фиды (сервисы «RSS → письмо»); список адресов — личные данные подписчиков, отдельное решение |
| **Аналитика и UTM** (§80) | на старте — без счётчиков на сайте; UTM-метки только по политике (выключены по умолчанию), канонический адрес чистый; сокращатели ссылок — нет (зависимость, гниение ссылок, приватность); первичная аналитика без cookies (у хостинга или самохостинг) — решение фазы 10 |
| **Приложение и бот** (§83, §85) | читают `/api/v1/` и `/feed.json`; версия в адресе — чтобы формат можно было менять без поломки клиентов |
