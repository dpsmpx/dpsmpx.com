# Устройство системы: монолит, события, учётные данные, надёжность

**Вопрос.** Как устроить систему публикации при текущем масштабе (один
автор, единицы публикаций в неделю, 6–7 площадок), чтобы она была
надёжной, заменяемой по частям и не требовала инфраструктуры
(`PLATFORM_VISION.md`, §15–18, §30–31, §36–38, §43–45, §55–57, §67–70,
§106–108, §115). Источники по площадкам — `PLATFORM_APIS.md`; по сайту —
`WEBSITE.md`. Решения — Д23–Д31.

## 1. Монолит, модульный монолит, микросервисы (§70)

| | Монолит | **Модульный монолит** | Микросервисы |
|---|---|---|---|
| Что | один код без внутренних границ | один процесс и пакет; модули с явными интерфейсами (ядро, адаптеры, сайт) | отдельные сервисы, сеть, очереди |
| Когда оправдан | прототип | несколько предметных областей, одна команда | независимые команды, разные нагрузки и частоты выпуска |
| Цена | связность растёт | дисциплина границ | сеть, развёртывание, наблюдаемость, согласованность данных |

Нагрузка — единицы операций в день; команда — один человек и сессии
ИИ; данные — файлы в Git. Распределённость не даёт ничего, кроме цены.
**Вывод: модульный монолит** — один пакет `tools/cs` с модулями
`core/` (модель и движок публикации), `adapters/` (площадки, по
одному на площадку, за общим интерфейсом), `site/` (генератор сайта).
Граница проверяется: ядро не импортирует адаптеры площадок, кроме
реестра (тест).

## 2. Очередь и планировщик (§74, §115)

- Очередь заданий — **журнал публикаций в Git** (append-only JSONL):
  запись «запланировано» с временем; запуск `publish --due` берёт
  наступившие. Распределённой очереди нет (§115).
- Запускает автор (вручную или своим планировщиком ОС на своей
  машине — там же учётные данные). Облачной службы нет.
- Отложенная публикация средствами площадки (VK `publish_date`, YouTube
  `publishAt`) — опционально в адаптере; у Telegram и Discord её нет —
  только наш планировщик.

## 3. События и вебхуки (§36–38)

| Способ | За | Против |
|---|---|---|
| Вебхук GitHub → приёмник | мгновенно | нужен публичный адрес и сервер (у статического сайта нет) — против §33 |
| Функция на краю хостинга | без своего сервера | ещё одна среда исполнения; секрет вебхука у хостинга |
| **Опрос** (`GET /releases`, теги) при запуске | без сервера; работает офлайн-первым | задержка до следующего запуска |

**Вывод:** события — **опрос источников при запуске** (`events poll`),
нормализация в `data/releases/` и черновик кампании, без публикации.
Повторное событие (тот же релиз дважды) не создаёт второй черновик —
ключ события (источник + id). Вебхуки — позже, если появится
хостинг с функциями.

## 4. Транзакционная публикация и идемпотентность (§15–18, §56)

Площадки не дают транзакций: «опубликовать» нельзя откатить, а
нативная защита от дублей есть только у VK (`guid`, 1 час). Шаблон
**журнал намерений**:

1. `prepare` — собрать запрос из одобренной версии; ключ идемпотентности
   = хэш (объект, вариант, версия варианта, адресат, окружение).
2. `validate` — предпроверка: адресат, аккаунт, язык, ссылки, медиа,
   время, версия = одобренная (§51).
3. Запись `PUBLISHING` в журнал **до** вызова площадки.
4. `publish` — вызов адаптера.
5. `verify` — адаптер подтверждает: есть удалённый id и адрес (или
   чтение поста).
6. `record` — `PUBLISHED` с id и адресом или `FAILED` со структурной
   ошибкой.

Повторный запуск: есть `PUBLISHED` по ключу — пропуск; есть
`PUBLISHING` без исхода (обрыв, таймаут) — **исход неизвестен**: повтор
только после проверки на площадке (адаптер умеет найти пост) или
решения автора — иначе возможен дубль. Это и есть «retry after
timeout» из §56.

**Повторы** (§17): только для временных ошибок (`RATE_LIMITED`,
`PLATFORM_UNAVAILABLE`, сетевые), экспоненциальная задержка с
дрожанием, потолок попыток, каждая попытка — запись в журнале.
`AUTH_EXPIRED`, `PERMISSION_DENIED`, `INVALID_CONTENT`, `MEDIA_REJECTED` —
не повторяются: нужен человек.

**Лимиты** (§57) — в адаптере, свои у каждой площадки (Telegram
`retry_after`, Discord заголовки маршрутов, YouTube суточные корзины,
VK ошибка 6).

## 5. Учётные данные (§30–31, §55)

| Где хранить | За | Против |
|---|---|---|
| **Переменные окружения** процесса | просто, без зависимостей, не на диске в репозитории | видны дочерним процессам; легко «утечь» в лог |
| Хранилище ОС (Keychain, Secret Service, Credential Manager) | шифрование ОС | зависимость от библиотеки и ОС |
| Зашифрованный файл (age/sops, `pass`) | переносимо, можно в резервную копию | ключ расшифровки — ещё один секрет |
| Облачный менеджер секретов | ротация, аудит | облако и аккаунт ради нескольких токенов |

**Вывод:** интерфейс «хранилище учётных данных» с реализацией
**переменные окружения** (по имени из `credential_ref` адресата);
другие реализации — по необходимости. Граница — **площадка ×
окружение**: у staging и production разные имена переменных, общий
токен у тестового и рабочего адресата — ошибка проверки. Проверка
здоровья видит наличие и срок, но не значение. Ротация по видам —
`docs/operations/CREDENTIALS.md`.

## 6. Офлайн-первым (§67–68, §108–109)

Создание, факты, черновики, правка, версии, предпросмотр, проверки,
сборка сайта — без сети и без внешних API. Сеть нужна только адаптеру
в момент публикации. Недоступна площадка — запись остаётся
`SCHEDULED`/`FAILED (retryable)`, канонический материал не трогается.
Недоступен провайдер ИИ — объект остаётся черновиком. Сайт недоступен —
публикация в соцсети допускается только если канонический текст уже в
Git (политика, `data/policy/publication.yaml`).

## 7. ИИ как поставщик (§43–45, §86–87)

- Интерфейс `GenerationProvider` с реализациями по необходимости:
  сейчас — `session` (текст пишет сессия Claude Code в репозитории) и
  `template` (детерминированная подстановка фактов). Внешние API —
  когда понадобятся.
- Кэш генерации: ключ = хэш (промпт, входы, контекст, модель,
  параметры); результат с хэшем; повтор без изменения входов берётся из
  кэша.
- Вывод ИИ — **непроверенный** (`trust: unverified`) до прохождения
  валидатора; одобряет только автор. У агентов нет рабочих токенов и
  права одобрения — роли (`docs/content/GOVERNANCE.md`).

## 8. Наблюдаемость (§106–107)

Структурные записи (JSON по строке) в каталоге сборки build/logs (не в Git):
id публикации, кампании, площадка, попытка, задержка, код ошибки,
метаданные ответа площадки — **после вычистки секретов** тем же
сканером, что `secrets`. Журнал публикаций в Git — только итог без
ответов площадок целиком. Проверка здоровья: адаптеры, учётные данные
(есть / нет / срок), сайт (сборка), хранилище (Git чистый, давность
резервной копии), провайдер ИИ.
